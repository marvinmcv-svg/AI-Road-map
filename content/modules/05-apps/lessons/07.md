## Lesson objectives
By the end, the student can…
- Explain the difference between saving on the phone and saving in the **cloud**.
- Add **sign-up and log-in** to their app with Supabase.
- Make sure each user only sees **their own data**, and keep the secret key secret.

## Words for today
- **Cloud** — computers on the internet that store your data, so you can reach it from any device.
- **Database** — a place that stores tables of data, like a very strong spreadsheet.
- **Login (sign in)** — proving who you are, so the app knows which data is yours.
- **Row Level Security (RLS)** — a database rule: each person can only see and change their own rows.
- **Public key vs. secret key** — the public key can be in your app (only with RLS on). The secret key must NEVER be in your app or repo.

## 1. Warm-up — Lost phone (10 min · 1-on-1: 5 min)
```teacher
Today your app saves data in the cloud, with a login. Then it works on any device. Imagine you lose your phone. Where is your data?
```

Imagine you lose your phone. Where is your app's data now? Open your app on a laptop. Is your data there? Why not?

```solo
Open the student's app on your laptop next to their phone. Different data! Ask: "How do big apps fix this?"
```

## 2. Mini-lesson — Cloud + login + privacy (15 min · 1-on-1: 10 min)
Show **Visual 1**: **phone and laptop → login → cloud database → each user's own rows.**

**How Supabase fits in:**
1. Make a Supabase **project**. It has a database and login built in.
2. Make a **table** from your data model (lesson 5), with a `user_id` column.
3. Turn on **Row Level Security** with a rule: "people can only see and change rows where `user_id` is their own."
4. Turn on **email login** (email + password, or a magic link).
5. Claude Code connects the app using the project's **URL** and **public key**.

**Key rules** (**Visual 2**):
- The **public** key can go in the app, but ONLY if Row Level Security is on for every table.
- The **secret** key never goes in the app, the repo, a chat or a screenshot.
- Put the URL and public key in **Vercel → Project → Settings → Environment Variables**, and ask Claude Code to read them from there.

## 3. Hands-on build — Cloud and login (40 min · 1-on-1: 28 min)
1. In Supabase: new project → make your table → turn on RLS → turn on email login.
2. Ask Claude Code:
```
Connect my app to Supabase. Project URL and public key will be in environment variables (I'll add them in Vercel): [names].
My table is [name] with columns [list], including user_id.
Add sign-up, log-in and log-out screens. Save and load data from Supabase instead of local storage, only for the logged-in user.
Tell me the exact Row Level Security rules to add in Supabase so users can only see and change their own rows, and how to test that it works.
Explain each step simply. Never put the secret key in the code.
```
3. Add the RLS rules Claude Code gives you (read them first: do they say "only your own rows"?).
4. Add the environment variables in Vercel, deploy, and test: sign up, add data, log out, log in on another device.

**Checkpoint 1 (+20 XP):** table with RLS on, and login works.
**Checkpoint 2 (+20 XP):** data follows the user to a second device, and the secret key is nowhere in the repo.

```group
Pairs check each other's repos: search for "secret" and "service" to make sure no secret key is in the code.
```

```solo
Do the Supabase steps side by side the first time: you on your demo project, the student on theirs. Then let them run the Claude Code part on their own.
```

> 🛡️ **Privacy moment:** you are now storing other people's data (if friends use your app). That's a big job to do well. Collect only what the app needs.

## 4. Game / challenge — Try to Peek (10 min · 1-on-1: 7 min)
Make 2 accounts. Add data with account A. Log in as account B. Can B see A's data? (It must not!) If yes, fix the RLS rule and try again.

```group
Every app that passes the peek test: +15 XP. Everyone who finds and fixes a leak: +5.
```

```solo
**Student vs. Bolt.** You make an account on their app and try to see their data. Then they try on your demo app. If nobody can peek, both win! +15 XP for passing, +5 for any leak found and fixed.
```

## 5. Share-out — Two devices (10 min · 1-on-1: 5 min)
Add something on your phone; show it appearing on a laptop after login.

```solo
The student shows the two-device test and explains RLS in their own words.
```

## 6. Exit ticket (5 min)
1. What's the difference between local storage and a cloud database?
2. What does Row Level Security do?
3. Which key can go in your app, and which must never?

```solo
Ask out loud. Run the test checklist from lesson 6 again. Did the cloud change break anything?
```

## Differentiation
- **Extra help:** login + one table only. Do the Supabase setup together, step by step.
- **Extra challenge:** add "Delete my account and all my data" (a real privacy feature), and test it.
- **1-on-1 tip:** this is a big step. If time runs out, finish the peek test first: a private app without sync is better than a synced app that leaks.
