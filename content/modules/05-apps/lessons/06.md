## Lesson objectives
By the end, the student can…
- Write a **test checklist** for every user story.
- Find bugs, read an error message, and write a bug report Claude Code can fix.
- Undo a bad change by going back to a saved version (**commit**).

## Words for today
- **Test case** — one thing to try, with the result you expect.
- **Debugging** — finding out why something is wrong and fixing it.
- **Error message** — the computer's note about what broke. Read it! It often says exactly where.
- **Console** — a hidden panel in the browser that shows error messages.
- **Commit** (again) — a saved version of your code. You can go back to it.
- **Regression** — something that used to work, but broke after a change.

## 1. Warm-up — Bug safari (10 min · 1-on-1: 5 min)
```teacher
Every builder makes bugs. Pros just get good at finding them. Today you are a bug hunter. You have 5 minutes. Go!
```

Use the buggy demo app. Find all 3 bugs in 5 minutes. For each one, say what you did and what went wrong.

```solo
Time it. Then ask: "Which bug would make a real user quit the app?"
```

## 2. Mini-lesson — The debugging loop (12 min · 1-on-1: 8 min)
Show **Visual 1**:
1. **Repeat it:** can you make the bug happen again, every time? Write the exact steps.
2. **Look:** open the Console. Any red error message? Copy it.
3. **Report:** give Claude Code the steps, what you expected, what happened and the error message.
4. **Fix and re-test:** test the bug AND the things around it (did the fix break something else?).

**A great bug report for Claude Code:**
"Steps: open Add, leave Amount empty, tap Save. Expected: a message 'Please add an amount'. Actual: the app shows a blank screen. Console error: [paste]. Please fix it and explain the cause simply."

**Going back in time:** every change Claude Code saves is a **commit**. If a change breaks your app, ask Claude Code: "The last change broke [thing]. Please undo it and go back to how it was before." Or look at the commit history on GitHub to see what changed.

## 3. Hands-on build — Test and fix your app (43 min · 1-on-1: 30 min)
1. Write a test checklist: at least 2 test cases per user story, plus 3 "weird" ones (empty, huge, fast double tap).
2. Run every test on your phone. Mark Pass or Fail.
3. For each Fail: follow the debugging loop and get it fixed.
4. Re-run the whole checklist after the fixes. Did anything else break (a regression)?
5. Practice going back once: ask Claude Code to make a small change you don't like, then undo it.

**Checkpoint 1 (+20 XP):** test checklist written and run, with Pass/Fail for each.
**Checkpoint 2 (+20 XP):** 3 or more bugs fixed with good bug reports, and the full checklist re-run.

```group
Pairs swap checklists and run each other's tests.
```

```solo
You are the tester for the first round. The student writes every bug report themselves, even if it's slower. Praise good bug reports more than quick fixes.
```

> 🛡️ **Error moment:** when you paste an error message into Claude, check it doesn't include any private data or secret keys.

## 4. Game / challenge — Bug Bounty (10 min · 1-on-1: 7 min)
Swap apps. Find as many bugs as you can in 5 minutes. A bug only counts with a full bug report (steps, expected, actual).

```group
Most bugs with full reports: +15 XP. Everyone: +5.
```

```solo
**Student vs. Bolt.** You each hunt bugs in the other's app for 5 minutes. Full bug reports only! +15 XP for playing, +5 for the win.
```

## 5. Share-out — Best bug of the day (10 min · 1-on-1: 5 min)
Share the sneakiest bug you found and how it got fixed.

```solo
The student tells the story of their trickiest bug like a detective case: clue, suspect, fix.
```

## 6. Exit ticket (5 min)
1. Name the 4 steps of the debugging loop.
2. What's a regression?
3. How do you undo a change that broke your app?

```solo
Ask out loud. Keep the test checklist. You'll run it after every big change.
```

## Differentiation
- **Extra help:** 1 test per user story plus 1 weird test. Use the bug report template word for word.
- **Extra challenge:** ask Claude Code to add tests that run by themselves for the data functions, and explain what each test checks.
- **1-on-1 tip:** reading error messages out loud takes away the fear. Do it together the first few times.
