## Lesson objectives
By the end, the student can…
- Write 3 to 5 **user stories** for their app.
- List every **screen** and draw the **user flow** between them.
- Test a **paper prototype** with a real person and fix what confused them.

## Words for today
- **User story** — "As a ___, I want to ___, so that ___." One thing the user needs.
- **Screen** — one page of an app (Home, Add, History, Settings).
- **User flow** — the path a user takes through the screens to get something done.
- **Tab bar** — the row of buttons at the bottom of an app to switch screens.
- **Paper prototype** — app screens drawn on paper, to test before building.
- **MVP (first version)** — the smallest version that still solves the problem.

## 1. Warm-up — Use a paper app (10 min · 1-on-1: 5 min)
Use your demo paper prototype: tap the paper "buttons" and the teacher swaps the screens. Try to log a habit. Where did you get stuck?

```solo
The student taps, you play "the computer" and swap sticky notes. Then swap roles with their idea.
```

## 2. Mini-lesson — Stories → screens → flow (12 min · 1-on-1: 8 min)
Show **Visual 1**:
1. **User stories** (what the user needs):
   - "As a student, I want to log a glass of water in one tap, so that it's not a chore."
   - "As a student, I want to see my streak, so that I stay motivated."
2. **Screens** (where it happens): Home · Add · History · Settings.
3. **User flow** (the path): Home → tap "+" → Add → Save → back to Home with the new count.

**Rules for a great first version (MVP):**
- 3 to 5 user stories, no more. Extra ideas go on a "Later" list.
- Every story should take **3 taps or fewer**.
- A **tab bar** with 2 to 4 tabs is easy for thumbs.

## 3. Hands-on build — Plan and paper test (38 min · 1-on-1: 27 min)
1. Write 3 to 5 user stories (and a "Later" list for the rest).
2. List the screens. Draw each one on a phone sheet: title, buttons, what's shown.
3. Draw the user flow with arrows, one flow per story.
4. Ask Claude: "Here are my user stories and screens: [paste]. Which story has no screen? Which flow takes more than 3 taps? What would confuse a new user?" Fix your plan.
5. Make it a paper prototype: one screen per sticky note or sheet.

**Checkpoint 1 (+20 XP):** 3 to 5 user stories + a "Later" list.
**Checkpoint 2 (+20 XP):** all screens drawn + a user flow for each story.

```group
Pairs check each other's flows: can each story be done in 3 taps or fewer?
```

```solo
Ask the student to explain each flow while pointing at the screens. Count the taps out loud together.
```

## 4. Game / challenge — Paper App Test (15 min · 1-on-1: 10 min)
A tester gets a task ("Log 2 glasses of water and check your streak"). The maker plays the computer and swaps paper screens. The maker doesn't explain anything! Note every spot where the tester gets stuck.

```group
Test with someone from another house. Fewest stuck spots after one fix: +15 XP. Everyone: +5.
```

```solo
**Student vs. Bolt.** You test their paper app; they test yours. Count stuck spots. Fix one thing and test again. +15 XP for playing, +5 for fewer stuck spots the second time.
```

## 5. Share-out — Plan tour (10 min · 1-on-1: 5 min)
Walk through your flows. What did the paper test change?

```solo
Take phone photos of every paper screen and the flows. You'll give them to Claude Code in lesson 4.
```

## 6. Exit ticket (5 min)
1. Write one user story for your app.
2. What's a user flow?
3. Why test on paper before building?

```solo
Ask out loud. Put the "Later" list somewhere safe: it's a great extension list.
```

## Differentiation
- **Extra help:** start with 3 user stories and 3 screens. Use a ready-made screen sheet with a tab bar drawn in.
- **Extra challenge:** add one "edge case" flow: what happens when there's no data yet, or the user makes a mistake?
- **1-on-1 tip:** be a confused tester on purpose. The more the student watches someone struggle, the better their plan gets.
